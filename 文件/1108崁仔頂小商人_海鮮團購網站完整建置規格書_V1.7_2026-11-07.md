# 1. 專案定位與目標

## 1.1 品牌

-   中文名稱：基隆鮮物．崁仔頂小商人
-   英文／羅馬字：khàm-tíng
-   核心業務：崁仔頂現流海鮮選品、冷凍常態商品團購。
-   延伸方向：崁仔頂導覽預約、魚類教育資訊、會員制度、營運資料分析。

## 1.2 網站核心定位

本網站不是一般大型電商的固定商品型錄，而是以崁仔頂市場現流選品為特色的團購平台：

1.  現流商品是首頁主角，強調每日限量、供應變動及即時搶購。
2.  冷凍常態商品提供穩定、可持續選購的商品清單。
3.  顧客可將現流與冷凍商品放在同一購物車結帳。
4.  同一顧客在指定週期內的商品金額可累積，用於運費級距及出貨資格判斷。
5.  初期採銀行轉帳及人工對帳，不串接銀行帳戶。
6.  後台需協助管理者處理商品、庫存、訂單、付款、出貨及營運資料。
7.  系統優先解決人工整理訂單、付款核對、庫存及出貨錯誤，特別是深夜結單與盤點工作。

## 1.3 設計原則

-   現流優先、冷凍常態輔助。
-   操作直覺，降低顧客下單步驟。
-   庫存與訂單交易必須可靠，不以動畫代替真實資料。
-   重要管理操作必須可追溯。
-   前台不公開顧客個資及敏感匯款資料。
-   先完成可營運的基本系統，再擴充會員、導覽及 AI。
-   手機版是必要驗收項目，不可只完成桌面版。
-   不承諾跨週寄庫；跨週合併僅屬管理者個案裁量。

# 4. 商品與上架管理

## 4.1 商品類型

1.  每日現流商品（fresh）：供應量受漁獲影響，限量、每日變動。
2.  冷凍常態商品（frozen）：長期陳列、持續販售，依庫存管理。

每個商品至少保存： - product ID - 商品類型 - 商品名稱 -
規格／重量／包裝單位 - 售價 - 商品圖片 - 商品說明 -
商品狀態（草稿、已排程、上架、售罄、下架、封存） - 建立及更新時間 -
建立者／更新者 - 價格歷史或價格 snapshot 關聯 - 商品排序與分類

商品下單後，訂單明細必須保存商品名稱、規格、單價等
snapshot，不可因後續商品改名或改價而改變歷史訂單。

## 4.2 現流上架排程（CONFIRMED）

-   例行上架：每週二至週六，中午 12:00。
-   週日中午 12:00：允許額外上架現流商品。
-   管理者可在任何時間手動上架，不受例行時段限制。
-   週六中午 12:00 是最後一次例行上架時間，不是停售時間。
-   已上架商品週六 12:00 後仍可購買，除非售完或管理者下架。
-   週日及非例行手動上架商品，依訂單成立當下的有效 `weekly_cycle_id`
    歸屬。
-   上架排程、週期切換及結算是三個獨立事件。

## 4.3 商品管理功能

-   新增、編輯、複製、下架、封存。
-   快速上架。
-   複製歷史商品及規格。
-   設定價格、數量、單位、圖片、描述。
-   設定排程上架及手動立即上架。
-   查看商品銷售數量及歷史價格。
-   商品上下架需留下管理者及時間紀錄。
-   需有售罄狀態及錯誤輸入檢查。

# 5. 庫存與防超賣

## 5.1 核心原則（CONFIRMED）

-   現流與冷凍商品均由後端庫存資料作為唯一依據。
-   前端選擇數量、加入購物車，不代表保留庫存。
-   訂單成功建立時，後端 transaction 立即扣庫存。
-   未付款訂單也已扣庫存，不自動釋放。
-   不可只靠前端 JavaScript 或即時動畫宣稱防超賣。
-   併發下單必須由 Firestore transaction 或等效原子交易保證。

## 5.2 下單交易流程

1.  前端提交商品 ID、數量及顧客資料。
2.  後端重新讀取商品狀態、價格、庫存。
3.  驗證商品仍可購買、數量合法、庫存足夠。
4.  在同一原子交易中扣減庫存並建立訂單及訂單明細。
5.  成功後回傳訂單資訊。
6.  庫存不足或商品已下架時，拒絕訂單並回傳最新狀態。
7.  不可相信前端傳入的價格、運費或商品名稱。

## 5.3 前端數量選單

-   現流商品：+1 至 +10。
-   冷凍商品：+1 至 +6。
-   預設 +1。
-   最大可選數量不得超過目前可售庫存。
-   庫存變動時更新選單範圍。
-   不允許 0、負數或超過庫存的數量。
-   送出時後端再次驗證。

## 5.4 現流庫存即時呈現

-   現流商品剩餘數量需明顯顯示。
-   當後端真實庫存變動時，透過即時監聽更新畫面。
-   `stockBump3X`：成功扣庫存後，實際剩餘數量可短暫放大／閃動，約 0.8
    秒。
-   動畫只能由真實後端資料變更觸發，不可在前端假扣庫存。
-   避免同一更新重複播放動畫。
-   尊重 reduced-motion 使用者設定。
-   其他買家看到的數字更新，必須反映後端最新可售數量。

## 5.5 庫存帳務區分

需區分： - physical on-hand：實際盤點在手數量。 -
available-to-sell：目前可供新訂單購買數量。 - outstanding fulfillment
commitment：已成立但尚未完成履約的數量。 - 未付款訂單占用。 -
已付款未出貨。 - 已出貨。 - 人工調整及損耗。

月底盤點報表不得重複計算已出貨或已被訂單占用的數量。

## 5.6 人工調整、取消及退款

-   訂單取消／退款不自動補庫存或扣減庫存。
-   管理者決定是否回補、回補數量及原因。
-   每次調整需記錄調整前後數量、原因、管理者、時間及關聯訂單。
-   原始庫存交易紀錄不可覆寫。
-   所有庫存調整採追加式紀錄（append-only audit trail）。

-   結帳時重新驗證價格、商品狀態及庫存。
-   購物車資料不可作為庫存保留依據。

## 6.2 顧客結帳（CONFIRMED）

-   顧客不需要 Google 登入，可訪客結帳。
-   收集必要資料：姓名、手機、Email、收件資料。
-   顧客週累積身分使用系統 customer ID，並以驗證過的
    Email、電話及安全流程識別。

-   查單應使用安全 token、Email 驗證或等效機制。
-   個資不得公開於留言板或前台公開資料。

## 6.3 訂單資料

每筆訂單至少需保存： - order ID - customer ID - 訂單成立時間 - 商品明細
snapshot - 商品原價與小計 - 運費 snapshot - 應付總額 - 付款狀態 -
訂單狀態 - `weekly_cycle_id` - `settlement_period_id`／結算納入紀錄 -
shipment batch 關聯 - 顧客收件資料 snapshot - 取消／退款狀態 -
管理者備註及操作紀錄

## 6.4 訂單狀態建議

狀態應明確區分，不可把付款、履約、取消混成一個欄位： - created／待付款 -
payment_reported／已回報待對帳 - payment_mismatch／金額不符 -
paid_verified／已人工確認收款 - fulfillment_pending／待出貨 -
assigned_to_shipment／已加入出貨批次 - shipped／已出貨 -
completed／已完成 - cancellation_pending／取消處理中 -
cancelled／已取消 - refunded／已退款（可另記退款金額及時間）

實際狀態模型需避免不合法跳轉，並保留完整狀態時間軸。

# 7. 週期、結算與週累積

## 7.1 三個獨立概念（CONFIRMED）

必須分開管理： 1. 現流商品上架排程。 2.
營運接單週期（`weekly_cycle_id`）。 3.
結算期間（`settlement_period_id`）。

三者不得綁成同一個排程。

## 7.2 週累積

-   同一顧客本週商品金額累積。
-   不同顧客不可合併計算。
-   週累積包含未付款訂單。
-   每筆訂單建立時寫入 `weekly_cycle_id`。
-   週期切換後不可回寫舊訂單的 cycle ID。
-   取消訂單後，週累積由管理者人工調整；保留原始數值與調整原因。
-   週累積應能查詢計算明細，不可只保存一個無法追溯的總數。

## 7.3 結算時間

-   初始結算時間：每週日 23:55:00，時區 Asia/Taipei。
-   週日 23:55 是結算，不是週期切換。
-   倒數只是前端展示，不控制後端接單。
-   結算納入需有唯一紀錄，避免重複結算或漏算。

## 7.4 週期切換

-   週期切換採例行自動排程。
-   特殊情況可由管理者提前、延後或立即切換。
-   切換前需預覽受影響訂單及狀態。
-   記錄管理者、操作時間、原定時間、實際時間及原因。
-   切換不轉移舊未完成訂單。
-   舊訂單保留原 weekly_cycle_id、付款、結算、出貨及取消歷史。
-   舊出貨資格與既有出貨批次不因週期切換自動改變。
-   結算完成至實際切換前建立的訂單，仍掛當時 current
    weekly_cycle_id，但納入下一個尚未完成的 settlement period。
-   管理者調整結算時間的生效規則仍待確認。

## 7.5 首頁團購資訊卡

顯示： - 明確日期及星期。 - 目前接單週期。 -
本次累積結帳期間（若與接單週期不同，分開顯示）。 - NT\$3,000
出貨門檻。 - 顧客本週累積金額及距離門檻差額（僅本人可見）。 -
結算倒數。 - 週日仍可下單的提示。 - 週六 12:00
是例行現流最後上架時間，不是訂單截止。 -
顯示資料以後端權威設定為準，不可用前端本機日期或 ISO week 自行猜測。

# 8. 運費、出貨與跨週合併

## 8.1 運費級距（CONFIRMED）

以同一顧客適用週累積的商品原價計算，運費不列入級距：

  商品累積金額              運費
  -------------------- ---------
  NT\$0--2,000（含）     NT\$130
  NT\$2,001--2,999        NT\$60
  NT\$3,000 以上            免運

-   出貨門檻：NT\$3,000。
-   級距以商品原價計算，不把運費算入。
-   若未來引入折扣、調整價或補差額，級距基礎如何計算需另行確認。
-   系統應保存當次計算 snapshot，不因日後級距修改而改變歷史訂單。

## 8.2 出貨規則

-   例行出貨日：每週二及週三。
-   鮮度期限：10 天。
-   鮮度起算日由管理者設定，例如實際到貨日或其他確認日期；不可自動用下單日推定。
-   出貨批次與訂單分開管理。
-   出貨批次需有 ID、日期、物流單號、運送方式、收件資料、狀態。
-   管理者可合併／拆分訂單、選擇運送方式、設定運費、列印及匯出出貨清單。
-   多筆訂單可合併至一個出貨批次；一筆訂單可拆分，但必須留下拆單紀錄。
-   一筆訂單不得同時進入多個 active shipment
    batches，除非管理者執行並記錄拆單。

## 8.3 收件門市

匯款及收件回報保留： - 第一備用超商：7-ELEVEN／全家、店名、店號。 -
第二備用超商：7-ELEVEN／全家、店名、店號。 -
實際出貨前需確認門市具冷凍取貨資格，並符合包裹尺寸／重量限制。 -
收件資料應保存於訂單 snapshot，修改時保留異動紀錄。

## 8.4 跨週合併（管理者個案裁量）

對外公開規則： - 每週出貨。 - 不接受跨週寄庫。 -
不對外宣傳例行跨週合併或承諾顧客可跨週累積。

內部管理規則： -
管理者可基於商品保存、履約進度、運費經濟及營運考量，個案核准未出貨訂單跨週合併。 -
已出貨訂單不可合併。 - 管理者需搜尋同一顧客未出貨訂單，查看原
cycle、商品、原商品原價、原已收運費、合併後運費及差額。 -
管理者人工選擇舊運費退款、折抵、不退不折或其他方式；系統不可自動退款或折抵。 -
若合併無利益，管理者可維持原出貨安排。 -
合併需記錄原訂單、操作人、時間、原因、批次及金額歷史。 - 合併不得改變原
weekly_cycle_id、商品明細／價格 snapshot、週累積、結算歷史或付款紀錄。 -
合併只影響 shipment batch 與 freight 的管理結果。 -
未出貨合併可以調整或取消。 -
不得把「不跨週寄庫」解讀成「禁止管理者個案跨週合併」。 -
實際跨週商品保存及暫存條件尚未確認，不能推定保存政策。

# 9. 付款、匯款回報與 Email 通知

## 9.1 付款方式

-   初期採銀行轉帳。
-   銀行入帳由管理者人工核對。

## 9.2 訂單成立 Email

訂單成功建立後： - 寄送顧客訂單成立通知。 - 管理者收到通知或副本。 -
內容包含訂單號、商品明細、金額、運費、匯款資訊及安全回報入口。 - Email
寄送由受保護的後端服務處理。 - 寄信失敗需記錄並可重試。 - 防止重複寄信。

## 9.3 匯款及收件資料回報

Email CTA 開啟安全回報表單： - 訂單號：自動帶入、唯讀，不可自行修改。 -
匯款金額。 - 匯款帳戶末五碼或交易代碼（欄位定義仍待確認）。 -
收件人姓名。 - 收件人手機。 - 第一備用超商及店名／店號。 -
第二備用超商及店名／店號。 - 出貨偏好
A／B／C（選項意義需以最終營運規則確認）。

安全要求： - token 隨機、不可猜、有期限、可撤銷。 -
不可透過修改訂單號查詢別人資料。 - 重送更新同一 report
或保留版本，不得產生無限重複列。 -
回報寫入資料庫後，付款狀態為「待人工對帳」。 - 通知管理者處理。

## 9.4 Email Dispatcher

至少包含： - 訂單成立通知。 - 匯款／收件回報通知。 - 14 天未付款提醒。 -
3 天寬限期屆滿後自動取消通知。 - 付款確認通知。 - 出貨通知。 -
管理者異常通知。

每次寄信記錄： - 事件 ID - 收件人 - 模板版本 - 寄送時間 - 寄送結果 -
失敗原因 - 重試次數 - 防重複 idempotency key

API key、SMTP 密碼及其他 secrets 不得放在前端或 Git repository。

# 10. 未付款逾期與取消

## 10.1 已確認規則

    上述未確認前，不得自行新增寬限或豁免條件。

# 15. 技術架構與資料安全

## 15.1 建議技術架構

-   前端：React + TypeScript + Vite。
-   身分驗證：Firebase Authentication。
-   資料庫：Cloud Firestore。
-   圖片／附件：Firebase Storage。
-   安全交易及排程：Firebase Cloud Functions。
-   Email：後端 Email API service。
-   原始碼：GitHub。
-   部署：Firebase Hosting 或經評估的相容平台。
-   Google Sheets 僅作報表匯出或輔助分析，不作第二個可寫主資料庫。
-   Firebase 為正式資料唯一 source of truth。

## 15.2 建議資料集合（Collections）

實際 schema 需由 `DATA_MODEL.md` 維護，以下是架構預留清單： -

`settlement_inclusions` - `message_boards` - `faq_items` -
`admin_users` - `audit_logs` - `email_events` - `operations_logs` -
`system_settings` - `memberships`（未來） -
`membership_payments`（未來） - `member_reservations`（未來） -
`tours`、`tour_sessions`、`tour_bookings`（未來） -
`fish_species`、`fish_api_sources`、`fish_api_cache`（未來）

## 15.3 安全原則

-   Firestore Security Rules 採最小權限。
-   顧客不可讀取其他顧客個資、訂單及付款資料。
-   管理者權限由伺服器端驗證。
-   庫存扣除、價格驗證、運費計算、訂單建立等敏感操作由後端執行。
-   Email token 必須安全、隨機、有期限及可撤銷。
-   XSS 防護及輸入驗證。
-   API secrets 不得放前端或提交 Git。
-   敏感資料不得寫入公開集合。
-   管理操作必須留下 audit log。
-   定期備份，並實際測試還原程序。
-   開發、內部測試及正式環境分離。
